1. Evolução dos Bancos de Dados

Os SGBDs evoluíram em resposta às mudanças nas máquinas (RAM, disco, processadores), nos ambientes (arquitetura, redes) e nos tipos de carga de trabalho (workload).

LINHA DO TEMPO Anos 60–70 ──▶ Bancos de dados de rede e hierárquicos Anos 70–hoje ──▶ Banco de dados relacional (OLTP / OLAP / SQL) Anos 90–hoje ──▶ Banco de dados orientado a colunas Anos 00–hoje ──▶ Banco de dados orientado a documentos (NoSQL) Banco de dados de grafos Banco de dados distribuídos Anos 10–hoje ──▶ Banco de dados in-memory (NewSQL) Bancos paralelos e distribuídos de nova geração
Termos: OLTP e OLAP

OLTP (Online Transaction Processing) — cargas de trabalho transacionais: muitas escritas e leituras pontuais, curtas e concorrentes. Ex.: sistema de caixa, e-commerce.

OLAP (Online Analytical Processing) — cargas analíticas: poucas consultas mas muito complexas, varrendo grandes volumes de dados. Ex.: relatórios de BI, data warehouse.

A motivação principal para o surgimento do NoSQL e NewSQL foi a inadequação dos SGBDr tradicionais para dois novos requisitos:

  • Necessidade de maior desempenho em aplicações de Big Data e Web 2.0.
  • Necessidade de maior flexibilidade no schema e no modelo de dados.

3. NoSQL ("Not Only SQL")

3.1 Características Gerais

Bancos NoSQL foram desenvolvidos para se adequar às demandas da Web moderna, Big Data e ambientes distribuídos. Não seguem os princípios ACID dos SGBDr e operam segundo o Teorema CAP.

Termos: ACID

ACID é o conjunto de propriedades que garante a confiabilidade de transações em SGBDr tradicionais:

  • Atomicity (Atomicidade) — uma transação executa por inteiro ou não executa. Nunca a meio.
  • Consistency (Consistência) — uma transação leva o banco de um estado válido a outro estado válido, respeitando todas as restrições.
  • Isolation (Isolamento) — transações concorrentes não interferem umas nas outras; o resultado final é equivalente à execução serial.
  • Durability (Durabilidade) — após confirmada (commit), a transação persiste mesmo em caso de falha de sistema.

Principais características:

  • Escalabilidade horizontal — adicionar mais nós à medida que o volume cresce, em vez de apenas melhorar o hardware de um único servidor (escala vertical).
  • Schemaless — sem esquema predefinido; estrutura dos dados pode variar entre registros.
  • Sem relacionamentos explícitos (chaves estrangeiras) e sem transações entre múltiplos agregados.
  • Linguagem de consulta menos poderosa que SQL; acesso geralmente via API.
  • Suporte a replicação mestre-escravo e ponto a ponto (P2P).
  • Suporte a particionamento horizontal (sharding).
  • Orientado a agregados de dados (exceto grafos).
  • Seguem princípios CAP e BASE — consistência eventual no lugar de consistência imediata.

3.3 Agregados

Um agregado é uma coleção de objetos relacionados tratados como uma única unidade de dados nos sistemas NoSQL. É o equivalente, no NoSQL, ao conceito de "entidade com todos os seus atributos aninhados".

Propriedades:

  • Estrutura mais complexa que uma tupla relacional.
  • Modificações são operações atômicas.
  • Unidade natural de replicação e particionamento.
  • Facilita o funcionamento em clusters: o agregado sinaliza quais dados devem estar no mesmo nó, minimizando transferências de rede.
  • Reduz a incompatibilidade de impedância — a estrutura aninhada de um agregado é mais próxima dos objetos em memória do que tabelas relacionais, facilitando a manipulação pelas aplicações.
Termo: Impedância (Impedance Mismatch)

No modelo relacional os dados são representados como tabelas de linhas, enquanto as aplicações trabalham com objetos (classes, structs). O esforço de mapear entre esses dois mundos é chamado de impedância. Agregados NoSQL resolvem parcialmente esse problema porque sua estrutura hierárquica (JSON/BSON) reflete diretamente a estrutura dos objetos da aplicação.

Exemplo de agregado (pedido de e-commerce):

{
  "_id": "pedido_1001",
  "data": "2026-05-02",
  "cliente": {
    "nome": "João Silva",
    "email": "joao@email.com"
  },
  "itens": [
    { "produto": "Notebook", "preco": 3500.00 },
    { "produto": "Mouse",    "preco": 50.00 }
  ],
  "endereco_entrega": {
    "rua": "Rua A",
    "cidade": "Rio de Janeiro"
  }
}

Problemas dos Agregados

  • Sem integridade referencial — não há equivalente a chave estrangeira entre agregados distintos.
  • Opacidade para o sistema — o NoSQL não consegue usar a estrutura interna do agregado para decisões de replicação e fragmentação automáticas.
  • Sem atomicidade entre múltiplos agregados — transações ACID se limitam a um único agregado; não há transações cross-aggregate.
  • Reflete o acesso, não os dados intrínsecos — o agregado é modelado conforme a aplicação acessa os dados; se houver necessidade de acessar os mesmos dados de formas diferentes, o modelo pode se tornar inadequado.

3.4 Modelos de Distribuição de Dados

Dados podem ser distribuídos em múltiplos nós por meio de duas estratégias ortogonais, que podem ser combinadas:

┌─────────────────────────────────────────────┐ │ DISTRIBUIÇÃO DE DADOS │ │ │ │ Fragmentação Replicação │ │ (sharding) (cópias) │ │ dados diferentes + mesmos dados │ │ em nós diferentes em múltiplos nós │ │ │ │ ────────────────────────────────────────── │ │ Fragmentação + Replicação combinadas │ └─────────────────────────────────────────────┘

Fragmentação (Sharding)

Dados diferentes são armazenados em nós diferentes. No NoSQL, a fragmentação ocorre no nível dos agregados.

Termo: Sharding (Particionamento Horizontal)

Sharding é a divisão de uma coleção de dados em partes menores (shards) distribuídas entre vários servidores. Cada servidor é responsável apenas por um subconjunto dos dados, distribuindo a carga de leitura e escrita. No mundo relacional, o equivalente é a fragmentação horizontal — dividir uma tabela por linhas entre servidores. O sharding aumenta a escalabilidade horizontal mas não oferece resiliência por si só: se um nó falhar e não houver réplica, os dados nele contidos ficam indisponíveis.

Princípios de fragmentação de agregados:

  • Localidade geográfica — dados ficam nos nós onde são mais consumidos, reduzindo latência de rede.
  • Equilíbrio de carga — dados distribuídos para equilibrar a sobrecarga entre os nós.
  • Fragmentação lógica — a aplicação define como os dados são distribuídos pelos nós do cluster.
  • Autofragmentação nativa — o próprio banco gerencia a alocação e redistribuição de fragmentos automaticamente.

Fragmentação no modelo relacional (referência):

  • Horizontal (sharding) — divide a tabela por linhas entre servidores; útil para alto volume e distribuição de carga.
  • Vertical — divide a tabela por colunas; útil para otimizar I/O em consultas que acessam poucos atributos.

Replicação

Os mesmos dados são copiados para múltiplos nós, aumentando disponibilidade e resiliência.

Mestre-EscravoPonto a Ponto (P2P)
EstruturaUm nó mestre (primário), demais são escravos (cópias)Todos os nós têm o mesmo peso
LeituraEscravos ampliam capacidade de leituraQualquer nó atende leituras
EscritaApenas o mestre; gargalo em writesQualquer nó; alta escalabilidade de escrita
ResiliênciaEscravos podem assumir se mestre falhar (failover)Perda de qualquer nó não afeta disponibilidade
Risco principalInconsistência se réplica não for propagada antes da falha do mestreConflito escrita-escrita se dois nós atualizarem o mesmo dado simultaneamente
Vantagens
  • Modelo simples: um único ponto de escrita evita conflitos de concorrência
  • Consistência mais fácil de garantir (especialmente com propagação síncrona)
  • Boa para workloads de leitura pesada
  • Sem ponto único de falha — alta disponibilidade de leitura e escrita
  • Escala horizontalmente tanto reads quanto writes
  • Sem eleição de novo mestre em caso de falha
Desvantagens
  • Mestre é gargalo de escrita; não escala writes com mais nós
  • Failover manual ou semiautomático pode introduzir janela de indisponibilidade
  • Com propagação assíncrona, escravos podem retornar dados desatualizados
  • Conflitos de escrita-escrita são mais prováveis e exigem resolução (vetores de versão, CRDTs)
  • Consistência mais difícil de garantir — tende a consistência eventual
  • Complexidade de coordenação maior entre nós

Propagação no modelo mestre-escravo:

  • Síncrona — mestre aguarda confirmação dos escravos antes de confirmar o commit; garante consistência, mas aumenta latência.
  • Assíncrona — mestre confirma o commit sem aguardar os escravos; menor latência, mas aceita consistência eventual — a leitura pode retornar uma versão antiga do dado até que a réplica seja propagada.

3.5 Consistência, Teorema CAP e BASE

Conflitos de Consistência

Sem controles rígidos de transação, dois tipos de conflitos podem ocorrer em sistemas distribuídos:

  • Conflito escrita-escrita — dois clientes escrevem sobre o mesmo agregado simultaneamente.
  • Conflito leitura-escrita — um cliente lê um dado inconsistente de um nó enquanto outro nó ainda está sendo atualizado (causas: latência, erros de rede, sobrecarga).

Estratégias de Resolução

  • Pessimista — previne o conflito antecipadamente:
    1. Bloqueia o agregado durante a operação (lock).
    2. Grava as duas versões conflitantes e deixa o usuário/sistema decidir qual usar.
  • Otimista — assume que conflitos são raros; detecta e trata o conflito após o fato.

Mecanismos NoSQL para Conflitos

Locks (Bloqueios)

Bloqueios no nível de agregado — podem ser locais (dentro de um nó) ou globais (cluster). Um lock garante acesso exclusivo ao agregado durante a operação, evitando leituras ou escritas concorrentes no mesmo dado.

MVCC — Multiversion Concurrency Control

O que é MVCC?

MVCC (Controle de Concorrência por Múltiplas Versões) é um mecanismo que mantém múltiplas versões de um mesmo dado simultaneamente, em vez de sobrescrever o valor diretamente. A ideia central é: leituras nunca bloqueiam escritas, e escritas nunca bloqueiam leituras.

Funcionamento básico:

  1. Cada escrita cria uma nova versão do dado, em vez de modificar o original.
  2. Leituras enxergam a versão mais recente confirmada no momento em que a transação começou — independentemente de escritas concorrentes que ainda não foram confirmadas.
  3. Versões antigas são removidas pelo processo de garbage collection quando não são mais necessárias por nenhuma transação ativa.

Variantes:

  • MVCC otimista (ex.: Hekaton, HyPer) — sem locks durante a transação; conflito é verificado apenas no final (commit). Se houver conflito, todas as transações menos uma são abortadas.
  • MVCC pessimista (ex.: SAP HANA) — usa versões para leituras mas aplica locks de registro para escritas, garantindo consistência mais forte.

A desvantagem do MVCC é a sobrecarga de criar e gerenciar múltiplas versões na memória, além do custo do garbage collection para remover versões obsoletas.

Teorema CAP

Proposto por Brewer (2000), o teorema afirma que um sistema distribuído só pode garantir duas das três propriedades a seguir simultaneamente:

Consistência (C) /\ / \ / \ / CP \ / ── \ / CA AP \ /______________\ Disponibilidade (A) Tolerância a Partições (P)
PropriedadeDescrição
Consistência (C)Todos os clientes veem exatamente os mesmos dados ao mesmo tempo, em qualquer nó do cluster.
Disponibilidade (A)Todo nó ativo responde requisições dos clientes sem falha.
Tolerância a Partições (P)O cluster continua funcionando mesmo que a comunicação entre alguns nós falhe (partição de rede / split brain).
Termo: Split Brain

Split brain ocorre quando uma falha de rede divide o cluster em dois (ou mais) grupos de nós que não conseguem mais se comunicar entre si. Cada grupo continua atendendo requisições de forma independente, podendo levar a versões divergentes dos mesmos dados. É um dos problemas mais graves em sistemas distribuídos e motivou o surgimento do teorema CAP.

Classificação de sistemas NoSQL sob o CAP:

  • CA — consistência + disponibilidade (sem tolerância a partições): não é viável em sistemas verdadeiramente distribuídos.
  • CP — consistência + tolerância a partições: em caso de partição, alguns nós ficam indisponíveis para garantir consistência.
  • AP — disponibilidade + tolerância a partições: em caso de partição, retorna dados possivelmente desatualizados, mas sempre responde.

Propriedades BASE

Alternativa ao ACID para sistemas NoSQL, as propriedades BASE descrevem um modelo mais flexível:

SiglaNomeSignificado
BABasically AvailableO sistema garante disponibilidade dos dados via replicação nos nós — em algum momento os dados estarão disponíveis.
BSSoft StateO estado do sistema pode mudar ao longo do tempo mesmo sem novas entradas, por causa da propagação de réplicas. A consistência não é garantida a todo instante.
BASEEventually ConsistentO sistema se tornará consistente em algum momento do futuro — não há garantia de quando, mas há garantia de que convergirá.

3.6 Persistência Poliglota (Polystores)

A persistência poliglota é a prática de usar diferentes sistemas de armazenamento para diferentes tipos de dados de uma mesma aplicação, escolhendo o banco mais adequado para cada problema.

Um polystore é um sistema que integra múltiplos bancos heterogêneos sob uma interface unificada:

  • Um Query Engine recebe a consulta (Q) e a decompõe em subconsultas (SQ) direcionadas a cada sistema.
  • Wrappers traduzem cada SQ para a linguagem nativa (Q') do banco de destino (SQL, Cypher, API REST, etc.) e integram os resultados.
Aplicação │ ▼ Query Engine ──▶ SQ₁ ──▶ [Wrapper SQL] ──▶ SGBDr SQ₂ ──▶ [Wrapper JSON] ──▶ MongoDB SQ₃ ──▶ [Wrapper HDFS] ──▶ Hadoop │ ▼ Resultado integrado

Graus de acoplamento: baixo, alto ou híbrido. Exemplos: CloudMDSQL, PolyBase, SparkSQL, HadoopDB.

3.7 NoSQL — Chave-Valor

Modelo mais simples do NoSQL: pares <chave, valor> onde o valor pode ser qualquer estrutura de dados.

Características

  • O agregado é opaco — o valor é armazenado como um BLOB (Binary Large Object); o banco não enxerga a estrutura interna.
  • Acesso sempre pela chave; sem índices secundários.
  • Altamente particionável; depósito de dados implementado como tabela hash.
  • Máxima escalabilidade horizontal entre os modelos NoSQL.
Termo: Tabela Hash

Uma tabela hash (ou hash map) é uma estrutura de dados que mapeia chaves a valores em tempo médio O(1) — ou seja, o tempo de acesso é constante independentemente do tamanho da tabela. A chave é transformada por uma função de hash que determina a posição onde o valor será armazenado. Isso torna os bancos chave-valor extremamente eficientes para leituras e escritas pontuais.

Operações

insert(chave, valor)
fetch(chave)          → recupera o valor pela chave
update(chave, valor)
delete(chave)

Exemplo

ChaveValor
16título="NoSQL essencial"; ano="2014"; autor="Fowler"
Serraaltura="1,80"; nascimento="06-10-1970"
100título="Barbie"; ano="2023"; gênero="fantasia"

Exemplos de implementações: Riak, Redis, Apache Cassandra, Amazon DynamoDB, Voldemort.

3.8 NoSQL — Documentos

Evolução do modelo chave-valor: o valor é um documento estruturado (JSON, BSON, XML) que o banco consegue inspecionar e indexar.

Termos: JSON, BSON, DSE

JSON (JavaScript Object Notation) — formato de texto para representar objetos estruturados como pares chave-valor aninhados. Legível por humanos e muito usado em APIs Web.

BSON (Binary JSON) — versão binária do JSON usada pelo MongoDB. Mais eficiente para armazenamento e transmissão que o JSON puro; suporta tipos de dados adicionais como datas e binários.

DSE (Document Store Encoding) — termo genérico para qualquer formato de serialização de documentos: JSON, BSON, XML, MessagePack, etc.

Características

  • Documentos são árvores hierárquicas autodescritivas; podem conter documentos aninhados.
  • O banco enxerga a estrutura interna do documento (não é opaco).
  • Permite índices secundários sobre campos do documento.
  • Permite recuperar partes do documento sem carregar o agregado inteiro.
  • Documentos de uma mesma coleção podem ter estruturas distintas.
  • Sem bloqueios explícitos — consistência mais fraca que chave-valor.
  • Altamente particionáveis; suportam escalabilidade horizontal.

Exemplos de implementações: MongoDB, Couchbase, CouchDB.

3.9 NoSQL — Família de Colunas

Pares <chave, família de colunas>. Cada linha tem uma chave e um conjunto de colunas, mas diferentes linhas podem ter colunas diferentes.

chave da linha │ família "customer" │ família "orders" ──────────────────┼──────────────────────────┼────────────────────── cliente_001 │ col: nome="João" │ col: pedido_id="P1" │ col: cidade="RJ" │ col: valor=3550.00 cliente_002 │ col: nome="Maria" │ (sem pedidos) │ col: email="m@x.com" │

Características

  • Uma coluna pode ser uma supercoluna — um contêiner para outras colunas.
  • Uma família de colunas agrupa colunas geralmente acessadas juntas (equivalente a uma "tabela larga").
  • Altíssima escalabilidade: possível dividir tanto linhas quanto colunas em múltiplos nós.
  • Divisão de linhas por faixa de valores (range-based), não por hash — mais eficiente para buscas por intervalo de chaves.

Exemplos de implementações: Google Bigtable (precursor), HBase (sobre HDFS), MonetDB.

3.10 NoSQL — Grafos

Modelo baseado em vértices (nós/entidades) e arestas (relacionamentos), com pares chave-valor como propriedades de ambos.

(Pessoa: João) ──[AMIGO_DE]──▶ (Pessoa: Maria) │ │ [MORA_EM] [TRABALHA_EM] │ │ ▼ ▼ (Cidade: RJ) (Empresa: TechCorp)

Características

  • Grafos são DAGs — estruturas de dados de propósito geral para qualquer tipo de dado conectado.
  • Não são orientados a agregados — diferença fundamental dos demais NoSQL.
  • Suportam processamento transacional com propriedades ACID.
  • Percorrer relacionamentos é muito rápido — relacionamentos já estão persistidos, não precisam ser calculados via joins no momento da consulta.
  • Problema de fragmentação: grafos são difíceis de particionar em múltiplos nós sem cortar muitas arestas, por isso costumam ser mantidos em um único nó.
Termo: DAG (Grafo Acíclico Dirigido)

Um DAG (Directed Acyclic Graph) é um grafo onde as arestas têm direção e não existem ciclos. Na prática, grafos de propriedades usados no NoSQL não são necessariamente acíclicos — o termo é usado de forma ampliada para descrever qualquer estrutura de grafo direcionado adequada para modelar relacionamentos.

Classificação

  • Orientados a propriedades — tendência em Big Data/Data Science. Ex.: Neo4j (linguagem Cypher).
  • Orientados a semântica (RDF) — tendência em Web Semântica e grafos do conhecimento. Ex.: Virtuoso, GraphDB (linguagem SPARQL).
Termos: Cypher e SPARQL

Cypher — linguagem de consulta declarativa para grafos de propriedades, criada para o Neo4j. Permite expressar padrões de grafos de forma visual. Ex.: MATCH (p:Pessoa)-[:AMIGO_DE]->(a) RETURN a.nome

SPARQL — linguagem de consulta para dados RDF (Resource Description Framework), o modelo da Web Semântica. Dados RDF são triplas (sujeito, predicado, objeto). Ex.: SELECT ?nome WHERE { ?p rdf:type :Pessoa ; :nome ?nome }

3.11 Modelo MapReduce

MapReduce é um modelo de programação para processamento de grandes volumes de dados em ambientes distribuídos (Google, 2004). O armazenamento é fornecido por um DFS (Distributed File System) como HDFS.

Termo: DFS (Distributed File System)

Um sistema de arquivos distribuído armazena arquivos fragmentados em múltiplos servidores de um cluster, com replicação automática para tolerância a falhas. O HDFS (Hadoop Distributed File System) é o DFS mais usado no ecossistema Big Data, dividindo arquivos em blocos (tipicamente 128 MB) distribuídos entre os nós.

Pipeline

Entrada (arquivos no DFS) │ ▼ ┌──────────┐ │ MAP │ → transforma cada item em 0 ou mais pares <chave, valor> └──────────┘ │ ▼ ┌──────────────┐ │ SORT/SHUFFLE │ → agrupa todos os pares pela chave └──────────────┘ │ ▼ ┌──────────┐ │ REDUCE │ → para cada grupo de chave, produz um valor de saída └──────────┘ │ ▼ Saída (arquivos no DFS)

Exemplo — Contagem de Palavras

Entrada:  "Deer Bear River", "Car Car River", "Deer Car Bear"

Map:
  Deer→1, Bear→1, River→1
  Car→1,  Car→1,  River→1
  Deer→1, Car→1,  Bear→1

Sort/Shuffle:
  Bear  → [1,1]
  Car   → [1,1,1]
  Deer  → [1,1]
  River → [1,1]

Reduce:
  Bear→2,  Car→3,  Deer→2,  River→2

MapReduce é usado em análise de links, processamento de grafos, aprendizado de máquina, e muitas outras tarefas de Big Data. Frameworks principais: Hadoop MapReduce, Apache Spark.

Técnicas do NewSQL

O NewSQL incorpora técnicas de ambos os mundos:

  • Do SGBDr: processamento paralelo, in-memory e distribuído; tolerância a falhas e cluster failover; replicação síncrona; streaming de dados.
  • Do NoSQL: armazenamento e acesso chave-valor; persistência poliglota; sharding e particionamento vertical.
  • Exclusivo NewSQL: gerenciamento escalável de transações; polystores e IMDBs; acesso via SQL, NoSQL e HDFS; processamento HTAP.
Termo: Cluster Failover

Cluster failover é o processo automático pelo qual um cluster detecta a falha de um nó e redireciona o tráfego para nós saudáveis, sem interrupção perceptível para o usuário. Em bancos NewSQL, isso é implementado via replicação síncrona: o nó substituto já tem uma cópia atualizada dos dados e pode assumir imediatamente.

Problema que o NewSQL resolve

  • Engenharia de dados cara: manutenção e criação de ETL/ELT custam ~75% do processo de data analytics.
  • Consultas OLAP sobre dados legados podem ser um risco para negócios que exigem decisões em tempo real.
Termos: ETL e ELT

ETL (Extract, Transform, Load) — processo de extrair dados de uma fonte, transformá-los (limpeza, conversão, enriquecimento) e carregá-los em um destino (ex.: data warehouse). A transformação ocorre antes da carga.

ELT (Extract, Load, Transform) — variante moderna onde os dados são carregados crus no destino e a transformação ocorre depois, aproveitando o poder de processamento do próprio sistema de destino (comum em data lakes e ambientes cloud).

4.1 HTAP — Hybrid Transactional and Analytical Processing

HTAP é uma arquitetura que permite processamento transacional (OLTP) e analítico (OLAP) simultâneos no mesmo sistema, eliminando a necessidade de ambientes separados e pipelines ETL.

Arquitetura Tradicional (sem HTAP): Aplicação → SGBDr (OLTP) ──[ETL]──▶ Data Warehouse (OLAP) (horas/dias de atraso) Arquitetura HTAP: Aplicação → NewSQL/IMDB (OLTP + OLAP simultâneos) │ dados quentes disponíveis em tempo real para análise

O termo foi definido pelo Gartner em 2014 como arquitetura em memória. Em 2018 o conceito foi estendido (in-process HTAP) para não se limitar mais apenas a técnicas in-memory.

Vantagens do HTAP

  • Elimina a necessidade de ETL/ELT.
  • Armazena dados em vários formatos simultaneamente.
  • Reduz custos de engenharia de dados.
  • Data freshness — consultas analíticas em tempo real sobre dados quentes (recém inseridos/atualizados).

Trade-offs HTAP

Existe uma tensão entre dois objetivos:

  • Isolamento de carga de trabalho — separar OLTP e OLAP para não prejudicar um ao outro.
  • Atualização de dados (data freshness) — garantir que OLAP enxergue os dados mais recentes do OLTP.

Alto isolamento → baixa atualização. Baixo isolamento → alta atualização. O NewSQL equilibra esses dois objetivos.

4.2 Taxonomia dos Sistemas NewSQL

Dimensão 1 — Modelo de Transação

TipoDescrição

Conhecimento a prioriExige conhecimento prévio das colunas a processar antes da execução.
ACID completoACID totalmente suportado, com múltiplos níveis de isolamento (serialização, snapshot).
Termo: Snapshot Isolation

Snapshot isolation é um nível de isolamento de transações no qual cada transação enxerga um snapshot (fotografia) consistente do banco de dados do momento em que ela iniciou. Novas escritas de outras transações não afetam a visão da transação atual. É implementado via MVCC. Garante que uma transação nunca leia um dado parcialmente atualizado por outra transação concorrente, mas pode permitir write skew em casos específicos — por isso não é equivalente à serialização completa.

Dimensão 2 — Escalabilidade

TipoDescrição
LimitadaGerenciador de transações centralizado; escala até saturar.
LogarítmicaReplicação ROWA; escala bem em leitura. Usa 2PC para transações concorrentes em múltiplos nós.
LinearVálida apenas em clusters shared-nothing.
Termos: ROWA, 2PC e Shared-Nothing

ROWA (Read-One Write-All) — protocolo de replicação onde qualquer nó pode servir leituras, mas escritas devem ser propagadas a todos os nós antes de confirmar. Escala bem em leitura, mas não em escrita.

2PC (Two-Phase Commit) — protocolo distribuído para garantir que uma transação que envolve múltiplos nós seja confirmada (commit) ou abortada (rollback) de forma atômica em todos. Fase 1: coordenador pede voto a todos os participantes. Fase 2: se todos votarem "sim", confirma; caso contrário, aborta. Problema: se o coordenador falhar no meio do processo, os participantes ficam bloqueados.

Shared-Nothing — arquitetura de cluster onde cada nó tem sua própria memória e disco, sem compartilhamento de recursos. Isso facilita a escalabilidade linear porque adicionar nós não cria contenção em recursos compartilhados.

5. Banco de Dados In-Memory (IMDB)

IMDBs são SGBDs do tipo NewSQL que mantêm os dados permanentemente na memória RAM, eliminando o gargalo de I/O do armazenamento secundário.

A ideia surgiu nos anos 1990 (TimesTen, Altabase). O mercado global de IMDB é estimado em US$ 20 bilhões em 2029.

Por que IMDB se tornaram importantes?

  • Crescimento da capacidade de RAM com redução de custo por GB.
  • Lei de Moore: barateamento de processadores multicore.
  • Arquiteturas modernas: SIMD, NUMA, múltiplos sockets.
  • Big Data demandando alta vazão de processamento.
  • Aplicações modernas exigem análises de eventos em tempo real.
Termos: SIMD e NUMA

SIMD (Single Instruction Multiple Data) — extensão de arquitetura de CPU que permite executar a mesma operação em múltiplos valores de dados em paralelo com uma única instrução. Ex.: somar 8 pares de inteiros com um único opcode. Fundamental para IMDBs que precisam processar grandes vetores de dados na RAM em alta velocidade.

NUMA (Non-Uniform Memory Access) — arquitetura de servidor com múltiplos processadores onde cada CPU tem acesso mais rápido à sua memória local que à memória de outras CPUs. IMDBs precisam ser projetados para minimizar acessos a memória remota (cross-NUMA), priorizando a localidade dos dados.

Arquitetura Conceitual dos IMDB

┌──────────────────────────────────────────────────────┐ │ SQL Engine │ │ (Otimizador de Consultas + Index & Data Manager) │ │ Logs & Locks │ │ │ │ ┌────────────────────────────────────┐ │ │ │ DATA STORE (RAM) │ │ │ │ (dados quentes, índices, versões) │ │ │ └────────────────────────────────────┘ │ └──────────────────────────────────────────────────────┘ │ Log / Checkpoint ▼ ┌────────────────────┐ │ Armazenamento │ (HD/SSD — dados frios, logs, │ Secundário │ checkpoints, backups) └────────────────────┘

Vantagens

  • Baixíssima latência — dados já estão na RAM.
  • Insights em tempo real — análise de streaming de eventos.
  • Alta disponibilidade — consistência por padrão.
  • Suporte a SQL, ACID, OLAP e OLTP simultâneos (HTAP).

Desvantagens

  • Baixa durabilidade — dados voláteis; risco de perda em crash.
  • Custo — RAM ainda é mais cara que disco.
  • Arquitetura mais complexa e várias implementações distintas.

5.1 Conceitos Principais dos IMDB

Hot & Cold Data

Nem todos os dados precisam estar na RAM simultaneamente — isso seria ineficiente e custoso.

TipoArmazenamentoCaracterísticas
Dados quentes (hot)RAMAcessados com frequência, missão crítica, dados recentes
Dados frios (cold)HD/SSDEstáticos, históricos, acessados raramente

A solução é classificar os dados e definir critérios de transferência entre armazenamentos, com logging e checkpoints para garantir a persistência.

Organização de Dados

ModeloDescriçãoIdeal para
Orientado a linhas (NSM)Atributos de um registro armazenados contiguamente na memóriaOLTP — acessa todos os atributos de um registro por vez
Orientado a colunas (DSM)Valores de um mesmo atributo de todos os registros armazenados contiguamenteOLAP — acessa um atributo de muitos registros
Termos: NSM e DSM

NSM (N-ary Storage Model) — cada linha (registro) é armazenada inteira de forma contígua. Bom para OLTP porque inserir/atualizar um registro requer escrever numa região contígua.

DSM (Decomposition Storage Model) — cada coluna é armazenada de forma contígua. Bom para OLAP porque uma consulta que lê apenas 2 colunas de uma tabela com 50 colunas não precisa carregar o resto. Permite compressão eficiente de dados similares contíguos.

Particionamento de Dados

Alguns IMDBs (H-Store, VoltDB, Calvin) implementam particionamento, outros não.

  • Um banco é dividido em partições disjuntas e independentes.
  • Transações são executadas em paralelo em cada partição.
  • Desvantagem: uma transação que acessa múltiplas partições precisa aguardar até que todas estejam disponíveis.
  • IMDBs que usam particionamento frequentemente não implementam controle de concorrência — as transações dentro de cada partição executam serialmente, eliminando a necessidade de locks.

Indexação

  • Dados são organizados em blocos/páginas em memória (não em frames de disco como nos SGBDr).
  • Índices para acesso direto aos dados em RAM — podem ser do tipo hash ou T-Tree.
  • Páginas de tamanho fixo ou variável.
  • Uso de checksum para detectar erros de software (corrupção em memória).
Termo: T-Tree (Índice em Memória)

Uma T-Tree é uma árvore de busca balanceada otimizada para dados em memória principal (análoga à B-Tree, que é otimizada para disco). Cada nó armazena um intervalo de valores e ponteiros para os dados reais, permitindo buscas eficientes por intervalos em RAM. Alternativa moderna: árvores skip list ou estruturas baseadas em hashing.

Versionamento de Dados

Muitos IMDBs (Hekaton, HyPer, SAP HANA) implementam múltiplas versões dos dados:

  1. Uma modificação não sobrescreve o valor original na RAM — cria uma shadow version (versão sombra) em endereço diferente.
  2. Quando a modificação é confirmada, a versão sombra torna-se a versão atual.
  3. A versão anterior permanece no banco e é removida pelo garbage collection quando nenhuma transação ativa a referencia mais.

O versionamento facilita a implementação de MVCC e permite criar backups (snapshots) para tolerância a falhas.

Processamento de Consultas

IMDBs fazem análise e otimização de SQL de forma similar ao SGBDr, mas diferem na execução:

  • Alguns compilam transações em código de máquina nativo (stored procedures compiladas), evitando interpretação em tempo de execução. Ex.: VoltDB.
  • Desvantagem: o banco precisa conhecer as transações com antecedência, o que é difícil de implementar para workloads ad hoc.
Termo: Stored Procedure

Uma stored procedure é um procedimento SQL pré-compilado e armazenado no banco de dados. Pode ser chamado repetidamente sem recompilar, o que reduz latência. No contexto de IMDBs, VoltDB vai além e compila as stored procedures em código de máquina nativo, eliminando até o overhead do interpretador SQL.

5.2 Controle de Concorrência nos IMDB

Os principais mecanismos são:

MVCC (Multiversion Concurrency Control)

Já explicado na seção de NoSQL. Nos IMDBs:

  • MVCC otimista (Hekaton, HyPer): sem lock durante a transação; verificação de conflito apenas no commit. Se conflito, apenas uma transação vence — as demais são abortadas.
  • MVCC pessimista (SAP HANA): MVCC para leituras + locks ao nível de registro para escritas.
  • Custo: overhead de criar versões e de garbage collection para remover versões obsoletas.

Particionamento sem Concorrência

IMDBs com particionamento (ex.: VoltDB) executam transações serialmente dentro de cada partição — sem locks, sem MVCC. Isso só é possível porque a partição é de thread única.

5.3 Recuperação de Falhas nos IMDB

Como a RAM é volátil, IMDBs implementam logging, checkpoint e recovery para garantir durabilidade:

IMDB (RAM) │ ├──[Logger]──▶ Log (disco): registra cada operação ou transação │ └──[CheckPointer]──▶ Snapshot (disco): fotografia completa do BD em um instante Em caso de falha: HD/SSD ──[Recovery]──▶ IMDB (RAM) restaurado a partir do último snapshot + logs
IMDBTipo de LogTipo de Checkpoint
HekatonOperaçãoVersões de dados
VoltDBTransaçãoSnapshot

Termos: Logging, Checkpoint e Recovery

Logging — registro contínuo de todas as operações ou transações realizadas, escrito em disco. Permite reconstruir o estado do banco após uma falha.

Checkpoint — snapshot completo do estado atual do banco gravado em disco em determinados intervalos. Reduz o tempo de recovery porque só é necessário aplicar os logs após o último checkpoint. Variantes: Naive (pausa o sistema), ZigZag, Piggyback (sobrepõe com operações normais).

Recovery — processo de restaurar o banco de dados a partir do checkpoint mais recente mais os logs subsequentes, recarregando tudo na RAM após uma falha.

O processo de logging tem overhead de I/O. Para minimizá-lo, técnicas como group commit (agrupar múltiplos logs em uma única escrita) e logs em SSD de alta velocidade são utilizadas.

6. Dúvidas

1. Por que NoSQL escala melhor horizontalmente?

SGBDs relacionais exigem coordenação entre nós para garantir consistência forte: JOINs buscam dados em servidores diferentes, transações distribuídas usam protocolos como 2PC, e validação de chaves estrangeiras requer comunicação cross-nó. Cada operação precisa "perguntar" a outros servidores antes de confirmar.

No NoSQL, o modelo orientado a agregados elimina essa dependência:

  • Cada operação acessa um único agregado que reside em um único nó — sem comunicação inter-nó para reads simples.
  • Sem chaves estrangeiras → sem validação cruzada entre nós.
  • Sem transações distribuídas → sem overhead de coordenação.
  • Autofragmentação: o banco redistribui agregados automaticamente ao adicionar nós.

Resultado: adicionar um nó ao cluster distribui a carga de forma quase linear. No relacional, adicionar nós sem refatorar o esquema não garante essa linearidade.

2. NoSQL permite transações sobre múltiplos agregados?

Em geral, não — e isso é uma escolha de projeto deliberada. A atomicidade no NoSQL se aplica apenas a um único agregado. Não há garantia de atomicidade entre múltiplos agregados.

Por que não? Transações distribuídas exigem protocolos de coordenação (como 2PC) que aumentam latência, reduzem disponibilidade e conflitam diretamente com os princípios BASE e o teorema CAP.

Exceções:

  • MongoDB (v4.0+) introduziu multi-document transactions com ACID, mas com custo de performance — vai contra os princípios originais do NoSQL e só é recomendado quando estritamente necessário.
  • Bancos de grafos (Neo4j) são uma exceção estrutural: suportam propriedades ACID completas, inclusive transações que abrangem múltiplos nós do grafo, porque não são orientados a agregados.

3. Como funcionam relacionamentos no NoSQL se não há chave estrangeira?

Existem três abordagens, e a escolha depende do modelo:

  1. Embedding (desnormalização) — dados relacionados são incorporados dentro do agregado. Ex.: o endereço do cliente fica dentro do documento do pedido. Uma única consulta retorna tudo. Desvantagem: duplicação de dados se o mesmo cliente aparecer em muitos pedidos.
  2. Referências manuais — um documento armazena o ID do documento relacionado (equivalente à FK, mas sem enforcement). A aplicação faz uma segunda consulta para buscar o relacionado. Não há JOIN automático no banco.
  3. Bancos de grafos — o relacionamento é um cidadão de primeira classe: uma aresta explícita entre dois nós, com propriedades. Permite consultas como "encontre todos os amigos de amigos de João que moram em SP" de forma nativa e eficiente.

Nos modelos chave-valor e colunar, relacionamentos praticamente inexistem no banco — toda a lógica de associação fica na aplicação.

4. O melhor suporte a particionamento horizontal se deve ao fato de escalar melhor horizontalmente?

São dois aspectos do mesmo fenômeno com a mesma causa raiz, não uma causa da outra. A causa fundamental é o modelo de dados orientado a agregados:

  • Um agregado é uma unidade auto-contida — sem dependências externas (sem FKs, sem JOINs necessários).
  • Isso torna o agregado a unidade natural de particionamento: pode ser movido para qualquer nó sem coordenação.
  • No relacional, um fragmento de tabela pode precisar de JOIN com outra tabela em nó diferente → comunicação de rede e coordenação obrigatórias.
  • No NoSQL, a consulta geralmente acessa um único agregado → um único nó → sem comunicação inter-nó.

O fluxo causal é: modelo orientado a agregados → particionamento horizontal simples → escalabilidade horizontal eficiente.

5. Consistência em ACID vs. CAP/BASE: são o mesmo conceito?

Não — são dois conceitos distintos que compartilham o mesmo nome, o que é uma fonte clássica de confusão:

Consistência ACIDConsistência CAP/BASE
NívelNível do banco de dadosNível do sistema distribuído
SignificadoO banco sempre passa de um estado válido para outro estado válido — respeita constraints, FKs, tipos, regras de negócioTodos os nós do cluster retornam o mesmo valor para um dado ao mesmo tempo — sincronismo entre réplicas
ExemploApós uma transferência bancária, o saldo total não muda — nenhuma regra de integridade foi violadaApós uma escrita no Nó A, uma leitura imediata no Nó B retorna o valor atualizado
BASE trata de...— (não é sobre ACID)Eventually Consistent: réplicas convergem para o mesmo valor eventualmente, mas podem estar desatualizadas por um período

Resumo: ACID consistência = integridade dos dados (não está corrompido). CAP consistência = sincronismo entre réplicas (todos veem o mesmo valor ao mesmo tempo).

6. Por que a opacidade do agregado é um problema para fragmentação e replicação?

O banco de dados trata o valor de um agregado como um blob opaco — ele conhece a chave, mas não enxerga a estrutura interna.

No modelo relacional, o sistema sabe que a coluna cidade existe na tabela clientes e pode usar isso para fragmentação inteligente: "todos os clientes de SP vão para o Nó A, todos do RJ para o Nó B" — fragmentação por predicado sobre conteúdo.

Em um NoSQL chave-valor puro (ex.: Redis), o banco não sabe que dentro do valor existe um campo cidade. Ele só pode fragmentar pela chave do agregado inteiro:

{
  "pedido_1001": { "cliente": { "cidade": "Rio" }, "itens": [...] }
}

O banco só enxerga "pedido_1001" — não consegue colocar automaticamente todos os pedidos do Rio no nó geograficamente mais próximo.

Consequências práticas:

  • Fragmentação automática por conteúdo interno é impossível sem lógica extra na aplicação.
  • A localidade geográfica dos dados depende de como a aplicação define a chave do agregado.
  • Índices secundários (ex.: MongoDB) "quebram" a opacidade e permitem consultas por campos internos, mas são uma extensão do modelo básico.

7. Qual a relação entre persistência poliglota e NewSQL?

São conceitos relacionados mas distintos em escopo:

ConceitoDefiniçãoEscopo
Persistência poliglotaArquitetura de software que usa múltiplos sistemas de armazenamento heterogêneos para diferentes necessidades (ex.: Redis para cache, MongoDB para catálogo, PostgreSQL para pedidos)Conceito arquitetural geral — independente de NoSQL ou NewSQL
PolystoresInfraestrutura técnica que unifica o acesso a múltiplos sistemas: um query engine decompõe uma query em subqueries nativas de cada sistema; wrappers traduzem entre o formato unificado e o nativo de cada bancoImplementação técnica da persistência poliglota
NewSQLCategoria de SGBDs que combinam SQL, ACID e escalabilidade horizontalCategoria de sistemas — pode ou não incluir suporte a polystores

Relação: polystores são uma característica opcional presente em alguns sistemas NewSQL (ex.: BigDAWG, SAP HANA). Mas persistência poliglota existe independentemente do NewSQL — você pode usar Redis + MongoDB + PostgreSQL juntos sem nenhum componente NewSQL. O NoSQL também se beneficia da ideia: a aplicação é que decide qual banco usar para cada tipo de dado.

Portanto: polystores fazem parte do ecossistema NewSQL como feature, mas não são sinônimos.

8. Qual o melhor representante da categoria NewSQL e por quê?

Google Spanner é o representante mais completo e academicamente relevante do NewSQL. Lançado internamente em 2007 e descrito em paper em 2012, foi pioneiro em combinar distribuição global, ACID e SQL.

Por que é classificado como NewSQL:

  • Modelo relacional com SQL — suporta Google Standard SQL com JOINs, transações e esquemas relacionais.
  • ACID completo e distribuído globalmente — transações com isolamento serializável entre data centers em diferentes continentes.
  • Escalabilidade horizontal linear — arquitetura shared-nothing; particionamento automático por intervalo de chave (key-range splitting) conforme o volume cresce.
  • HTAP — suporta workloads transacionais (OLTP) e analíticos (OLAP) no mesmo sistema.

Como armazena os dados logicamente:

  • Tabelas relacionais com chave primária obrigatória.
  • Interleaving — tabelas filho podem ser intercaladas fisicamente com as linhas pai, melhorando localidade de acesso para relacionamentos hierárquicos frequentes.
  • Particionamento automático por intervalo de chave; o sistema redistribui shards conforme o volume e o padrão de acesso.
  • Replicação síncrona baseada em Paxos entre zonas/regiões — maioria de votos confirma cada escrita.

Inovação central — TrueTime API:

O que é TrueTime?

O Spanner usa hardware especializado (relógios GPS e atômicos) em cada data center para disponibilizar uma API de tempo global chamada TrueTime. Em vez de retornar um instante exato, ela retorna um intervalo [t_earliest, t_latest] que garante conter o tempo real.

Isso permite ao Spanner atribuir timestamps causalmente corretos a transações globais sem precisar de comunicação adicional de coordenação: se o intervalo de uma transação A não se sobrepõe ao de B, o Spanner sabe com certeza qual aconteceu antes. Isso viabiliza serializable isolation global com latência muito menor que 2PC puro.

Outras características:

  • Disponibilidade de 99,999% (cinco noves).
  • Snapshot reads — leitura consistente de qualquer ponto no passado sem locks.
  • Amplamente adotado no Google (Ads, Gmail, Google Pay) e disponível como serviço gerenciado (Cloud Spanner).
